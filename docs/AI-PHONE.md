# AI-phone accessibility bridge

The existing package remains `com.dosa42.codexgoal`; this update is fixed at version 0.1.22/code 22. The service component is `com.example.aiphone.AiPhoneAccessibilityService`. Existing terminal, workspace, console, executor and voice code is preserved. The new service does not start microphone capture.

Android must enable the accessibility service before it can run. It connects outward to the resident Termux broker at TCP 127.0.0.1:8793 using UTF-8 NDJSON. Android owns its lifecycle. Healthy sockets do not expire. EOF/write failure triggers reconnection, a new UUID epoch and full state. The service does not replay requests on reconnect.

`app/src/main/assets/ai-phone.schema.json` contains the coordinator's full wire schema, including public executor file contracts implemented by the broker rather than this service. Native discovery returns that exact object and the SHA256 of its original bytes. WireSchema evaluates the constraints used by this contract for incoming frames before dispatch and outgoing frames. Unknown methods/parameters, malformed actions and stale handles fail before mutation.

All-display window enumeration is available from API 30; earlier Android exposes default-display windows only and advertises that limitation. Accessible children are traversed iteratively without node, depth or text caps. Identity-based cycle detection prevents infinite traversal. Full text and Android action lists remain available. Unmapped Android action IDs are labelled `android_action_ID` with `available:false`; no fake semantic handler is provided. Inaccessible window roots are reported in `unavailable`. Canvas pixels are not invented as text.

Android accessibility/display callbacks trigger coalesced snapshots. Initial connection emits a full state; changes emit typed deltas with baseRevision, changed nodes/windows and removals. `observe` provides full content or an explicit summary plus exact-schema selectors. Epoch/revision/display/window/node scope is checked again against current native identity before mutation.

Node actions target actual Android node handles. Global `performGlobalAction` has no display parameter and is truthfully `untargeted`; nonzero display requests are rejected. Its success only means accepted. App launch explicitly uses Android ActivityOptions.launchDisplayId (API 26+) and reports requested_display, not verified placement. Action/launch receipts initially say observedOutcome=unverified; subsequent events and broker predicates must establish the actual outcome. Screenshot global actions, if exposed by Android, are system actions; there is no screenshot-content or gesture observation transport advertised.

The private app SQLite mutation journal preserves immutable request IDs across process restart. Identical completed requests return the recorded response; conflicting payloads fail. A dispatch without a durable response remains uncertain and is never automatically repeated. There is no journal expiry or silent dedupe eviction.

Build tooling for this PC task is isolated under ignored `.build-tools/`. Source `.build-tools/env.sh`, then run `gradle :app:testDebugUnitTest :app:assembleDebug --console=plain --no-daemon`. Signing requires the existing matching ignored debug.keystore; never generate a replacement for an in-place update. Tests include existing baseline tests, native request rejection, persisted mutation journal semantics and the coordinator's 70 valid/invalid schema fixtures. Unit/Robolectric tests are not proof of installed phone behavior: deployment and phone0 acceptance belong to the browser/coordinator, preserving DeX and enabled services.

## Native identity and availability repair

Handles are assigned by Android `AccessibilityNodeInfo.equals` identity (source-node ID and window ID), additionally scoped by display/window. Identity keys retain separate untouched native copies. The same live node keeps its handle across traversal reordering; removal retires the handle, and replacement/reappearance allocates a new monotonically unique handle within the connection epoch. The platform API cannot reveal a provider reusing exactly the same native identity between observations, so this is not an assertion of provider-internal object lifetime. Production action validation rejects invalidated windows, compares the actual current native window root, refreshes a separate copy of the target node, and rechecks epoch/revision before dispatch. It does not traverse unrelated children or refresh identity-map keys.

`unavailable` participates in revision change detection. Any change to that array emits an authoritative full state instead of a delta, both when a root becomes inaccessible and when it recovers. Ordinary node/window changes continue to use deltas with the existing unchanged schema. Focused Robolectric tests execute the real service capture/action paths with distinct equal-looking Android nodes, reordering/removal/replacement, and cache reconstruction across root loss/recovery; they are not installed-device acceptance.


## Device-wide power leases (ai-phone/2)

The native `power` method combines process-owned public Android SCREEN_BRIGHT_WAKE_LOCK | ACQUIRE_CAUSES_WAKEUP locks with a shared display-0 accessibility window using FLAG_KEEP_SCREEN_ON. Its backend is `android_screen_wake_lock_with_accessibility_overlay`, with `holdDisplayId:0`. Wake has device scope and may affect both displays; callers cannot select a display. Each acquisition owns an independent native lock; leaseId equals requestId and preserves the caller owner. Default holds have no timeout. Only a caller's positive deadlineAfterMs adds a deadline. Explicit release targets the exact lease; releasing one lease does not release others. The last release removes the window. Service teardown removes the window but retains process-owned native leases; service rebind restores the window for those existing leases without reacquiring native wake locks. TCP reconnect leaves resources untouched. A new APK process starts empty with a new processInstanceId; persisted receipts never recreate holds.

The window is an 8dp blue indicator with TYPE_ACCESSIBILITY_OVERLAY, FLAG_NOT_FOCUSABLE and FLAG_NOT_TOUCHABLE. It passes input to the underlying app and uses the accessibility service's public display context/token. No activity is launched for hold. `backendHeld` and each lease's `held` require both the actual retained native lock and the attached, visible hold view. During attachment or service teardown they can be false while lease ownership still exists. Status also reads actual deviceInteractive, keyguardLocked and all display states. Resource attachment and lease transition outcomes do not assert screen illumination, keyguard dismissal or Settings readability. Events copy the exact power observation timestamp and retain the current transport epoch/accessibility revision without replacing accessibility state. Display, window attachment, screen/keyguard broadcasts and explicit deadlines produce observations. No wake heartbeat, artificial interaction, settings writes or hidden expiry is used. Protocol2 helloAck is required before request dispatch; old peers are refused.

WAKE_LOCK is declared. TURN_SCREEN_ON is also declared, but AOSP Android16 defines it as signature|privileged|appop, not a normal automatically granted permission. Wake capability describes availability of the public acquisition route, requiring screen-lock support plus the connected accessibility service and display 0. Inconclusive wake permission/app-op metadata is retained in `reason` and does not make an actually attemptable route unavailable: the installed intermediate candidate physically woke the phone despite this metadata. Availability is not a wake guarantee; results preserve actual before/after display state. Actual backend failures disable capability and become durable errors; inspect status rather than replaying uncertain mutations. The intermediate candidate also demonstrated that a retained native screen lock alone did not prevent this phone's 30-second timeout. The window route is a prototype requiring real-device continuous hold and underlying-app read/click proof; JVM attachment tests do not establish that result. Release removes our resources and does not force the screen off. Process-death cleanup and DeX preservation also require separate device validation.


## Targeted Home and explicit global actions

`home` takes requestId/displayId and resolves Android's default MAIN/HOME activity. A chooser, absent/disabled/unexported launcher, unsupported display or denied display launch returns an error. The actual component is launched with explicit ActivityOptions display ID and returned in the receipt, with scope=requested_display and outcome=unverified. There is no performGlobalAction fallback. Placement and preservation of the DeX Termux task require actual device observation. All untargeted global `act` requests now require scope=device, in addition to current handle epoch/revision and the existing display0 placeholder; this does not make them display-isolated.


Power observations carry a separate positive `powerRevision`, incremented on every actual capture under the process-owned manager monitor. The unbounded integer counter survives service/transport rebind and restarts only with the new processInstanceId. Status, mutation before/after, deadline and rebind captures all use this path. Event/result reuse of one capture preserves identical powerRevision, observedAt and payload. The outer event revision remains the accessibility revision. Consumers order current power observations by process identity and powerRevision, not wall-clock timestamps; historical receipts cannot establish current state or clear disconnect staleness.


Immutable receipt replay validates the stored response with an integer-preserving JSON tokenizer, then sends the original stored JSON unchanged. It never round-trips large power revisions through Android's default Double parser or re-dispatches a completed mutation. Duplicate acquire/release results remain historical even after release or service rebinding; current power status is a separate capture.


## Observation and control latency (release 22)

A serialized observation worker performs uncapped traversal, scoped full reads, app enumeration and bulk frame validation/serialization. Socket ingestion posts request admission to main without waiting for this worker. Power, Home, launch and node mutations remain on the Android main thread, with the existing exact receipt journal and lease ownership. A separate resident-reader worker can return summaries while a full capture is in flight. A single TCP writer still sends complete NDJSON frames: an already-writing large frame cannot be preempted. Device measurements must distinguish that transport cost and broker validation/event persistence from native operation time.

Accessibility events mark their window dirty; unknown scope invalidates all windows, and known display callbacks invalidate only that display. Events coalesce into one capture. Global, display and window invalidations have separate generations: a capture acknowledges only the generations for its actual scope, and later events for that scope retain their invalidation. A DeX event does not block phone0 acknowledgement. Known display callbacks invalidate that display; unknown event scope remains conservative. A failed capture is not continuously retried without another event/read. Explicit `observe(mode=full)` freshly traverses only the selected display/window. Unselected windows retain content, handles and original capture times; a newly enumerated unselected window is marked not captured until requested or invalidated. Filtered observations never replace the complete resident cache. There are no content, text, node or depth limits.

New full/summary observations explicitly emit `freshness` and `capturePending`. Summary retains the original selected-window capture time; it never reads the clock to make resident content appear new. Pending/invalidated content is stale only for the relevant target. `capturePending` reports active or scheduled capture work concerning that target, not unrelated DeX work. The all-display aggregate can remain stale while an actual selected phone0 capture is fresh. Node actions retain exact global revision checks plus target-specific invalidation checks; there is no new per-target wire revision. A merged resident state uses its oldest retained window capture time, while a selected full response uses its actual capture completion time. Freshness/pending or availability transitions publish a full state because the canonical delta does not type those fields. Other changes use atomic typed deltas. Neither revision changes nor native acceptance establish an observed action effect.

Each TCP connection has a new epoch. Queued work, capture commit and reply publication check their original epoch and queue; old reads cannot repopulate or publish into a new connection. Teardown retires node resources on the observation worker. Node keys are never refreshed in place. Temporary native nodes/windows are recycled on success, discard or failure.

`AiPhoneLatency` logcat JSON records request-correlated monotonic `atNs`/`durationNs` for arrival, dispatch, inbound validation, receipt lookup, operation, capture, outbound validation, serialization, receipt completion, output metadata-lock wait, enqueue-to-writer wait, actual socket write/flush and enqueue/receive completion. These are diagnostics, not wire or immutable receipt fields. The dispatch interval measures admission plus the selected lane's queue; operation includes its required native work, and capture includes serialization used for diffing. Stage intervals can overlap/nest and must not be blindly summed. No installed-device speed result is inferred from JVM tests. Focused regressions block actual production `getChild` traversal, prove control/resident completion through the actual loopback socket writer before release, reject old epoch captures, preserve other-display content, and check event invalidation and native handle validation.


A consumer keeps a selected capture's original revision/time immutable and maintains a separate current global action cursor. It may preserve that selection while advancing the cursor only across exact-base current-epoch/generation deltas proven unrelated to the target. Relevant changes, explicit target staleness, unknown gaps and peer replacement invalidate selection; a higher-revision full state also requires reseeding under this delta-only policy. The TUI creates a new immutable action request once with the evidenced cursor and selected node. Native still requires exact current global revision and validates target invalidation/native identity before journaling. Cursor changes never rewrite a request or historical receipt and never trigger hidden mutation retries. Production regressions demonstrate capture N/T + DeX-only delta N→N+1 + new accepted act N+1 while N/T remains unchanged; consumer delivery-gap knowledge remains the broker's responsibility.
